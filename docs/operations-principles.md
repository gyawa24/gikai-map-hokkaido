# 継続運用方針

最終更新: 2026-05-20

地方議会ドットコムは、機能を増やすこと自体を目的にしない。
長く続けられる環境、きれいなデータ、無理のない更新スケジュールを先に作る。

## 基本方針

### 1. 継続できる環境を作る

- 作業のたびに判断し直さない。追加、更新、検証、公開の手順を文書とスクリプトに寄せる。
- 手元だけで成立する作業を優先し、Vercel や外部APIに依存しすぎない。
- 個人利用のローカルデータと公開データを混ぜない。
- 1回きりの手作業で終わらせず、次回も同じやり方で回せる形にする。

### 2. 綺麗なデータを作る

- 画面側でバラバラなデータ差分を吸収しない。まず台帳、スキーマ、出典、公開状態を揃える。
- `data/{slug}/` を収集・編集の正、`site/data/{slug}/` を公開ビルドの入力として分ける。
- 公開導線は `site/data/_city-capabilities.json` を基準にし、手書きの `features` や個別ファイル直読みで判定しない。
- 予算、議事録、議決、速報、記事はそれぞれ性格が違うため、同じ「ある/ない」に潰さない。
- OCRやAI要約は入口であり、数字・氏名・発言内容は原典確認を前提にする。

### 3. スケジュールを持つ

- できる時に一気にやるのではなく、毎週・毎月・年度単位の運用リズムに分ける。
- 新しい機能追加より先に、既存データの健診と更新漏れの確認を行う。
- 追加候補は `docs/operations-board.md` に置き、Now / Next / Later の粒度で進める。
- ひとつの作業単位は、検証コマンドまで含めて終われる大きさにする。

## 判断基準

新しい作業を始める前に、次の3点を確認する。

1. この変更で、次回以降の運用が楽になるか。
2. この変更で、データの構造や出典がきれいになるか。
3. この変更で、次にやるべき作業が明確になるか。

この3つに当てはまらない改善は、急ぎの不具合修正を除き `Later` に置く。

## 標準スケジュール

### 毎回の作業開始時

- `git status --short` で未完了差分を確認する。
- 触る領域のドキュメントを読む。
- UI変更なら `DESIGN.md`、データ変更なら `docs/data-catalog-rules.md`、記事変更なら `docs/editorial/article-source-policy.md` を確認する。
- 作業の完了条件を短く決める。

### 毎回の作業終了時

- データ変更なら `node scripts/data-health.mjs --strict` を通す。
- 自治体単位の追加・更新なら `node scripts/verify-municipality.mjs <slug>` を通す。
- UIやNext.js実装を触ったら `npm run lint` と必要に応じて `npm run build` を通す。
- 更新情報に値する変更なら `site/data/news.json` の追記要否を確認する。
- 完了した作業、残った課題、次の候補を短く残す。

### 毎週

- `node scripts/operations-check.mjs --weekly` で現状と確認項目を表示する。
- `docs/operations-board.md` の Now / Next を見直す。
- `node scripts/data-health.mjs --strict` で公開データのズレを確認する。
- 直近で追加した自治体や予算OCRの出典リンクが切れていないか確認する。
- MCP検索や記事作成で使ったデータに、再利用できる抽出ルールがないか整理する。

### 毎月

- `node scripts/operations-check.mjs --monthly` で月次確認項目を表示する。
- `node scripts/data-health.mjs --strict` で公開データ全体の健診を通す。
- 未公開・再確認待ちの自治体をまとめて見直し、必要なら `minutes_verified_at` や出典確認日を更新する。
- `docs/municipality-coverage.md` と `docs/municipality-information-inventory.md` を最新化する。
- 予算書、議決結果、速報、議会だより、別feature候補を並べ替える。
- `site/data/budget_sources.json` の `取得候補` / `取込済み` / `保留` の意味が実データと合っているか確認する。
- `site/data/news.json` と `/news` の表示が、実際に公開した変更とズレていないか確認する。
- `docs/operations-board.md` の Now / Next / Later を、次の1か月で進める粒度に更新する。

月次レビューの成果物は、最低限次の4点にする。

- 今月追加・更新した公開データ
- 台帳・出典・ニュースで直したこと
- まだ公開しない候補と、その理由
- 来月の Now 1〜3件

`data-health` や `verify-municipality` が失敗している場合は、新しい取込を始めず、先に健診エラーを片付ける。

### 年度更新

- `node scripts/operations-check.mjs --yearly` で年度更新項目を表示する。
- 新年度予算書の公開状況を主要都市から確認する。
- 予算OCRは `budget_sources.json` で候補管理し、公開OCRが揃ったものだけ `取込済み` にする。
- 議員改選があった自治体は `members.json` と出典を優先して確認する。
- 議会の公開ページ構造が変わっていないか、主要スクレイパを小さく再検証する。

## データ更新の完了条件

データ更新は、ファイルを置いただけでは完了にしない。
次の状態になって初めて完了とする。

- 収集元 `data/{slug}/` と公開用 `site/data/{slug}/` の関係が明確である。
- 公開導線が capability 台帳に反映されている。
- 出典URLまたは確認元が追える。
- `verify-municipality` または `data-health` が通っている。
- UI上で「未確認」「取得候補」「取込済み」の意味が混ざっていない。

## 優先順位

1. データ台帳と検証ルールの整備
2. 既存データの品質確認と出典確認
3. 主要自治体の構造化追加
4. 検索・MCP・記事作成で使いやすい派生データの整備
5. UIの改善

UIは大事だが、データの信頼性を壊してまで急がない。
