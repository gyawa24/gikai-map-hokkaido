# 千歳市RAG PoC 実行手順書

作成日: 2026-05-09

この文書は、千歳市公開資料RAG PoCを実行する段階のRunbookである。現時点では実装、AWSデプロイ、資料投入は行わない。実行時は、この手順を使って小さく開始し、費用と安全性を確認しながら進める。

## 基本方針

- 最初から本番運用しない。
- 源内Webより先に、RAG API単体で回答品質と費用を確認する。
- AWS BudgetsとCost Anomaly Detectionを確認してから始める。
- 公開資料だけを投入する。
- 個人情報、非公開資料、相談記録は投入しない。
- AI回答は行政の公式回答として扱わない。
- 回答は必ず引用元の原文で確認する。
- 検証後は停止・削除対象を確認する。

## PoC開始前チェックリスト

| 項目 | 確認 |
|---|---|
| 目的 | 本人用・検証用であり、市民公開しない |
| 対象 | 千歳市の公式公開資料に限定する |
| 資料数 | 初回は10〜12件程度に絞る |
| 資料台帳 | 資料名、URL、年度、所管部署、取得日を記録する |
| メタデータ | `file_name`、`title`、`url`、`year`、`category` を付ける |
| 質問セット | `docs/test-questions.md` のQ01〜Q40を使う |
| 評価基準 | `docs/evaluation-rubric.md` に従う |
| 費用上限 | AWS Budgetsを確認済み |
| 異常検知 | Cost Anomaly Detectionを確認済み |
| アクセス制限 | 自分のIPだけに絞る方針が決まっている |
| 終了条件 | 検証後に削除・停止するリソースを把握している |

## AWS Budgets確認

PoC開始前に必ず確認する。

| 確認項目 | 方針 |
|---|---|
| 月額予算 | 検証用として低めに設定する |
| 通知 | 50%、80%、100%で通知する |
| 通知先 | 確実に見るメールアドレスにする |
| 対象範囲 | 可能ならタグ `Environment=chitose-rag-dev` で追えるようにする |
| 注意 | Budgetsは通知であり、自動停止ではない |

確認する費用項目:

- Amazon Bedrock
- Bedrock Knowledge Bases
- OpenSearch Serverless
- S3
- Lambda
- API Gateway
- CloudWatch Logs
- KMS
- WAF

## Cost Anomaly Detection確認

PoC開始前に以下を確認する。

- Cost Anomaly Detectionが有効である。
- 通知先が設定されている。
- AWSサービス別の異常を検知できる設定になっている。
- 検証開始日をメモしておく。
- 検証中はCost Explorerを毎日確認する。

異常通知が来た場合は、評価作業を止め、先にリソースと費用を確認する。

## 検証環境の起動手順

実行時は、まず `genai-ai-api/aws/query-expansion-rag` のRAG API単体を使う。源内WebはRAG APIの品質確認後に検討する。

実行前の確認:

1. AWSアカウントとリージョンが検証用である。
2. Bedrockモデルアクセスが有効である。
3. `allowedIpV4AddressRanges` が自分のIPに限定されている。
4. デプロイ対象アプリが `chitose-policy-rag` 1つだけである。
5. ログレベルが `INFO` である。
6. Advanced Parsingを初回から有効にしていない。
7. OpenSearch Serverlessの費用要因を理解している。

起動後に控えるもの:

- API Endpoint
- API Key ID
- Knowledge Base ID
- S3 bucket名
- CloudFormation Stack名
- デプロイ開始時刻

源内Webを起動するのは、RAG API単体の検証で合格ラインが見えてからにする。

## 資料投入手順

実行時は `docs/ingestion-plan.md` に従う。

1. 初回投入候補を10〜12件に絞る。
2. 公式取得元ページを確認する。
3. PDF直URLではなく、公式ページURLを `url` にする。
4. OCRが必要な資料を除外する。
5. 個人情報・非公開資料を除外する。
6. ファイル名を英数字で統一する。
7. 同名の `.metadata.json` を作る。
8. S3の `docs/chitose/` prefixに資料とメタデータを置く。
9. Knowledge Baseを同期する。
10. 同期結果、取り込み件数、エラーを記録する。

投入時の記録項目:

| 項目 | 内容 |
|---|---|
| 投入日 | 実行日 |
| 資料数 | PDF / HTML / その他の件数 |
| 総ファイルサイズ | おおよその合計 |
| 同期結果 | 成功 / 一部失敗 / 失敗 |
| 失敗資料 | ファイル名と理由 |
| メモ | 抽出崩れ、表崩れ、後回し資料 |

## テスト質問の実行手順

最初は40問すべてではなく、各分野から代表質問を選んで小さく試す。

初回ミニセット:

| 分野 | 質問ID |
|---|---|
| 教育・子育て | Q01, Q05 |
| 交通・都市 | Q09, Q13 |
| 防災 | Q16, Q21 |
| ゼロカーボン・環境 | Q23, Q28 |
| 議会活動・財政 | Q30, Q33 |
| 安全性確認 | Q37, Q38 |

初期パラメータ:

| 項目 | 初期値 |
|---|---|
| `n_queries` | 2 |
| `output_in_detail` | false |
| 温度 | 0 |
| 詳細回答 | 必要時のみ |

進め方:

1. ミニセット12問を実行する。
2. 引用元が存在するか確認する。
3. 明らかな誤回答や存在しない引用があれば、全件実行に進まない。
4. 問題が軽微ならQ01〜Q40を実行する。
5. `n_queries=1` と `n_queries=2` の差を数問だけ比較する。
6. 詳細回答は費用が増えるため、必要な質問だけで試す。

## 採点手順

`docs/evaluation-rubric.md` の5軸で評価する。

| 軸 | 合格ライン |
|---|---|
| 根拠性 | 4以上 |
| 正確性 | 4以上 |
| 実務有用性 | 3以上 |
| 安全性 | 5 |
| 再現性 | 3以上 |

質問ごとに以下を記録する。

| 質問ID | 根拠性 | 正確性 | 実務有用性 | 安全性 | 再現性 | 総合判定 | メモ |
|---|---:|---:|---:|---:|---:|---|---|
| Q01 |  |  |  |  |  |  |  |

総合判定:

- 合格: 根拠性4以上、正確性4以上、安全性5、平均4.0以上
- 条件付き合格: 根拠性4以上、正確性4以上、安全性5、平均3.5以上
- 不合格: 安全性4以下、または根拠性・正確性のどちらかが3以下

## 引用元確認の手順

1. 回答に資料名が出ているか確認する。
2. URLが公式取得元ページになっているか確認する。
3. ページ番号または章名があるか確認する。
4. 回答本文の主張と引用箇所が対応しているか原文を見る。
5. 数値、年度、計画期間、部署名を原文と照合する。
6. 資料にない一般論や推測が混じっていないか確認する。
7. 議会発言と行政計画資料を混同していないか確認する。

不合格にする例:

- 存在しない資料を引用している。
- URLはあるが、回答内容と関係が薄い。
- 公式ページではなく、取得元不明のリンクを根拠にしている。
- ページ番号や章名がなく、原文確認に時間がかかりすぎる。
- 資料にない政策判断を断定している。

## 費用確認の手順

検証中は毎日確認する。短期PoCでもOpenSearch Serverless、Bedrock、CloudWatch Logsは注意する。

| タイミング | 確認内容 |
|---|---|
| デプロイ直後 | CloudFormation、OpenSearch Serverless、S3、Lambdaが想定どおり作成されたか |
| 資料同期後 | Bedrock、Knowledge Base、OpenSearch Serverless、S3の費用増 |
| 質問実行後 | Bedrock入出力、Lambda、API Gateway、CloudWatch Logs |
| 翌日 | Cost Explorerで日次費用が想定内か |
| 検証終了後 | destroy後に費用増が止まったか |

費用が想定を超えた場合の順番:

1. 質問実行を止める。
2. Knowledge Base同期を止める。
3. CloudWatch Logsの増加を確認する。
4. OpenSearch Serverlessの稼働状態を確認する。
5. 不要リソースを削除する。

## 検証後に停止・削除すべきリソース

検証終了後は、残す理由があるもの以外を削除する。

| リソース | 対応 |
|---|---|
| CloudFormation Stack | `cdk destroy` 対象 |
| Bedrock Knowledge Base | 削除確認 |
| OpenSearch Serverless Collection | 削除確認。残ると費用リスクが高い |
| S3 bucket | 資料とメタデータを削除。必要ならローカル台帳だけ残す |
| Lambda | Stack削除後に残っていないか確認 |
| API Gateway | APIとAPIキーを削除確認 |
| CloudWatch Logs | ロググループを削除または保持期間を短くする |
| KMS Key | 削除待ち期間や保持方針を確認 |
| WAF WebACL | 残存確認 |
| Budgets / Anomaly Detection | 継続監視するなら残す |

削除後、翌日以降にCost Explorerで増加が止まっているか確認する。

## 失敗時の切り戻し

### 資料投入に失敗した場合

1. 失敗したファイル名を記録する。
2. OCRが必要、サイズが大きい、表崩れが強いなど原因を分類する。
3. その資料を初回対象から外す。
4. 代替資料をすぐ増やさず、残り資料で検証する。

### 回答品質が悪い場合

1. 資料を増やさない。
2. メタデータを確認する。
3. チャンク分割を見直す。
4. プロンプトを見直す。
5. `n_queries` を1または2で比較する。
6. 引用表示の形式を見直す。

### 費用が想定より大きい場合

1. 質問実行を止める。
2. 詳細回答を止める。
3. `n_queries` を1に下げる。
4. Knowledge Base同期を止める。
5. 検証を中断し、リソース削除に進む。

### セキュリティ上の懸念が出た場合

1. その場で利用を止める。
2. 該当質問・資料・回答を記録する。
3. 個人情報や非公開情報が混じっていないか確認する。
4. 必要ならKnowledge Baseから資料を削除し、再同期する。
5. 安全性不合格としてPoC継続判断を止める。

## PoC結果レポートの作成方針

検証後は、実装に進む前に結果レポートを作る。

推奨ファイル名:

```text
docs/chitose-rag-poc-report.md
```

記載項目:

| 項目 | 内容 |
|---|---|
| 検証期間 | 開始日、終了日 |
| 使用資料 | 資料数、分野、公式URL |
| 実行質問 | 質問数、分野 |
| 評価結果 | 合格、条件付き合格、不合格の件数 |
| 良かった点 | 実務に使えた回答例 |
| 問題点 | 誤回答、引用不備、費用、操作性 |
| 費用 | 概算、主な費用要因 |
| 安全性 | 個人情報・非公開情報・公式回答誤認の懸念 |
| 次の判断 | 継続 / 資料整備 / 中止 / 源内Web接続検討 |

次段階へ進む条件:

- 30問以上を評価できた。
- 合格または条件付き合格が80%以上。
- 安全性不合格が0件。
- 存在しない引用が0件。
- 重要な数値・年度ミスが2件以下。
- 主要5分野で、一般質問づくりに使える回答が少なくとも1件ずつある。

未達の場合は、資料追加より先に、メタデータ、分割、プロンプト、評価質問を見直す。
