# ローカル検索評価レポート

作成日: 2026-05-09

この文書は、AWS RAGに進む前に、ローカルのキーワード検索でチャンク設計と引用メタ情報が検索に耐えるかを確認した記録である。AWS、LLM API、RAG APIは使用していない。

## 評価の目的

RAG投入前に、抽出済み資料から生成したチャンクJSONLが、検索・引用確認に使える形になっているかを確認する。

特に見ること:

- 関連チャンクが上位に出るか
- 資料名とページ番号が検索結果に残るか
- `section` が結果理解に役立つか
- `excerpt` だけで内容の見当がつくか
- チャンクサイズが細かすぎないか、粗すぎないか

## 評価対象

| 項目 | 内容 |
|---|---|
| 資料 | 千歳市地域公共交通計画 |
| チャンクJSONL | `data/chunks/2025_chitose_public_transport_plan.jsonl` |
| チャンク数 | 60 |
| 平均文字数 | 約925文字 |
| 最小 / 最大 | 125文字 / 1,189文字 |
| 検索方法 | `scripts/local_search.py` によるキーワード検索 |

JSONL本文と検索結果全文は再生成物のためコミットしない。

## 試したクエリ

```bash
python3 scripts/local_search.py "公共交通 課題" --top-k 5
python3 scripts/local_search.py "バス 利用者 減少" --top-k 5
python3 scripts/local_search.py "高齢者 移動 手段" --top-k 5
python3 scripts/local_search.py "地域公共交通 計画 目標" --top-k 5
python3 scripts/local_search.py "交通空白" --top-k 5
```

## 結果概要

| クエリ | 上位結果 | 評価 |
|---|---|---|
| 公共交通 課題 | p.68-69、p.66-67、p.4など | 課題整理や計画背景に関係するページが上位に出た |
| バス 利用者 減少 | p.25-28「利用者数」 | 期待どおり。利用者数・減少に関するページが1位 |
| 高齢者 移動 手段 | p.15「交通動態」、p.52「通院の移動実態」など | 関連ページは出たが、語の組み合わせ次第で順位調整の余地あり |
| 地域公共交通 計画 目標 | p.72「地域公共交通の基本目標及び評価指標」 | 期待どおり。基本目標ページが1位 |
| 交通空白 | p.88-90付近の協議会議事一覧 | 該当語は拾えているが、本文説明ではなく議事一覧が中心 |

## 評価観点

### 関連チャンクが上位に出るか

主要クエリでは、おおむね関連チャンクが上位に出た。特に「バス 利用者 減少」と「地域公共交通 計画 目標」は、期待するページが1位になっており、チャンク分割とキーワード検索の組み合わせは最小検証として有効。

「公共交通 課題」は、課題そのもののページだけでなく、直前の取組・再編事業のページも上位に出ている。これは文脈としては有用だが、質問に直接答える根拠としては、p.68-70付近を人間が確認する必要がある。

### ページ番号が引用に使えるか

すべての検索結果に `source_title`、`source_file`、`page_start`、`page_end` が表示された。原文PDFに戻るための最低限の引用メタ情報は保持できている。

ページ範囲が複数ページにまたがる結果もあるが、最大でも数ページ程度であり、初回PoCでは許容範囲。

### section が検索結果理解に役立つか

`section` は多くの結果で役立っている。例として、「（2）利用者数」「4. 地域公共交通の基本目標及び評価指標」のような見出しは、検索結果の意味をすぐ判断できる。

一方で、表や議事一覧では「年度 会議 開催日時 議事」のような汎用的な見出しになることがある。RAG投入前に致命的ではないが、将来的には表・巻末資料の見出し補正を検討してよい。

### excerpt だけで内容の見当がつくか

多くの結果では、抜粋だけで内容の見当がつく。特に利用者数、基本目標、交通動態は、抜粋内に主要な説明が含まれていた。

表や議事一覧由来のチャンクでは、抜粋がやや読みにくい。これはPDF抽出と表構造の問題でもあるため、すぐにRAG投入資料を増やすより、必要に応じて表の整形や除外ルールを検討する。

### チャンクサイズが適切か

60チャンク、平均約925文字で、最小検証としては妥当。主要な本文ページは、1チャンクで文脈を保ちつつ、ページ番号で原文に戻れる粒度になっている。

短いチャンクは、目次末尾や巻末資料などで発生している。検索結果に出る場合は人間確認が必要だが、全体設計を止めるほどではない。

## 気になった点

- 「交通空白」は該当語を拾えているが、議事一覧が中心で、制度や施策の説明本文としては弱い。
- `section` が表や巻末資料では汎用的になりやすい。
- キーワード検索なので、「高齢者 移動 手段」のような質問では、語が直接出ているページに寄りやすい。
- 現時点では交通計画1件のみの検証であり、複数資料を入れた場合の資料間ランキングは未確認。

## 改善候補

すぐに必要:

- AWS RAGに進む前に、資料1件だけで最小検証する。
- BudgetsとCost Anomaly Detectionを先に設定する。
- 検索結果の上位チャンクを人間が原文確認する。

後で検討:

- 表・巻末資料の `section` 補正
- 目次や会議一覧を検索対象から弱めるルール
- BM25への差し替え
- ローカル埋め込み検索
- 複数資料投入時の資料間ランキング確認

## 判断

ローカル検索では、主要クエリに対して関連チャンクが取得できている。資料名、ページ番号、見出し、抜粋も検索結果に表示できており、RAG投入前のチャンク設計としては最小検証を通過したと判断する。

次はAWS RAG最小検証へ進んでよい。ただし、最初は資料1件のみとし、AWS BudgetsとCost Anomaly Detectionを設定してから行う。市民公開や本格運用には進まない。
