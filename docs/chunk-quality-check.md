# チャンクJSONL品質チェック手順

作成日: 2026-05-09

この文書は、`data/chunks/` に生成したJSONLを、RAG投入前に確認するための手順である。AWS、Bedrock、OpenSearch、RAG APIにはまだ投入しない。

## 目的

チャンクJSONLが、根拠確認しやすい構造になっているかを確認する。

特に見ること:

- 各行が有効なJSONか
- 必須項目が揃っているか
- `id` が重複していないか
- `text` が空または短すぎないか
- `text` が長すぎないか
- `char_count` が実際の文字数と一致しているか
- `page_start` / `page_end` が正しい範囲か
- `source_title` と `section` の欠落が多すぎないか

## 対象

対象は `data/chunks/` 配下の `.jsonl`。

JSONL本体は再生成できるため、Gitには入れない。

## 実行方法

標準出力で確認する。

```bash
python3 scripts/validate_chunks.py
```

特定ファイルだけ確認する。

```bash
python3 scripts/validate_chunks.py data/chunks/2025_chitose_public_transport_plan.jsonl
```

Markdownレポートを保存する。

```bash
python3 scripts/validate_chunks.py --write-report
```

保存先:

```text
reports/chunk-validation-report.md
```

`reports/` 配下のレポートは再生成できるため、通常はコミットしない。

## 必須項目

各チャンクに以下が必要。

| 項目 | 内容 |
|---|---|
| `id` | 安定したチャンクID |
| `source_file` | 元PDFまたは抽出元ファイル名 |
| `source_title` | 資料名 |
| `page_start` | チャンク開始ページ |
| `page_end` | チャンク終了ページ |
| `section` | 見出し候補。取れない場合は `null` 可 |
| `text` | 本文 |
| `char_count` | 空白を除いた文字数 |

## エラーと警告

### エラー

RAG投入前に必ず直す。

- JSONとして読めない行がある
- 必須項目がない
- `id` が空または重複している
- `text` が空
- `char_count` が数値ではない
- `char_count` と実際の文字数が一致しない
- `page_start` / `page_end` が数値ではない
- `page_start` が `page_end` より大きい
- `source_file` や `source_title` が空

### 警告

人間が確認し、許容するか判断する。

- `text` が短すぎる
- `text` が長すぎる
- `section` が欠落しているチャンクが多い
- 表紙、目次、巻末などで短いチャンクが残っている

短いチャンクがすべて悪いわけではない。表紙、目次、凡例、巻末資料では自然に短くなることがある。

## 閾値

初期値:

| 閾値 | 初期値 | 意味 |
|---|---:|---|
| `--short-threshold` | 200 | これ未満なら短いチャンクとして警告 |
| `--max-chars` | 1400 | これを超えたら長すぎるチャンクとして警告 |

チャンク生成側は800〜1,200文字を目安にしている。検証側は少し余裕を持たせ、1,400文字を超えたら警告にする。

## 人間が確認する観点

### 1. 資料名

- `source_title` が人間に分かる資料名になっているか。
- ファイル名だけになっていないか。
- 複数資料を混ぜたときに区別できるか。

### 2. ページ範囲

- `page_start` と `page_end` が入っているか。
- 範囲が広すぎないか。
- 原文PDFに戻って確認できるか。

### 3. 見出し

- `section` が見出しとして使えそうか。
- 目次、凡例、表の一部などが見出し扱いになりすぎていないか。
- 欠落が多い場合でも、ページ範囲で原文に戻れるなら初回PoCでは許容できる。

### 4. 本文

- `text` だけを読んで文脈が分かるか。
- 一文だけの短い断片になっていないか。
- 表や数値が説明文から切り離されすぎていないか。
- 長すぎて複数テーマが混ざっていないか。

### 5. ID

- `id` が重複していないか。
- 再生成しても大きく揺れないか。
- 後で評価結果と紐づけられるか。

## 初回PoCでの判断

そのまま次へ進める:

- エラーが0件
- 警告が短い目次・表紙・巻末程度に限られる
- `source_title` 欠落が0件
- `page_start` / `page_end` で原文に戻れる
- 主要本文チャンクが800〜1,200文字前後に収まっている

保留:

- 短すぎるチャンクが大量にある
- `section` 欠落が多く、ページ範囲だけでは文脈が追いにくい
- 長すぎるチャンクが多く、複数テーマが混ざっている
- 表や数値の対応が崩れている

やり直し:

- JSONLとして壊れている
- 必須項目が欠けている
- `char_count` が一致しない
- ページ範囲が不正
- 資料名が残っていない

## 次の作業

1. `scripts/chunk_text.py` でJSONLを生成する。
2. `scripts/validate_chunks.py` で構造・品質を確認する。
3. エラーがあればチャンク生成側を直す。
4. 警告は目視で確認し、許容できるものと直すものに分ける。
5. 問題がなければ、次にローカル検索またはRAG投入前台帳の整備に進む。
